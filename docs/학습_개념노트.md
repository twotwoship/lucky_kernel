### 학습의 목표

이양배의 역할은 수집 결과가 사용자에게 도달하는 경로를 구현하고 검증하는 것이다. 계획서에는 팀장, 개발 진단 콘솔, TCP 전송·Qt 분석 프로그램, 환경 구성이 배정되어 있으며, 상세 역할에는 STM32 시험 신호 생성과 송신값·해석 결과 비교도 포함된다. [P]

필요한 수준은 다음과 같다.

- **직접 구현 수준:** liblogic, 진단 CLI, TCP framing과 상태 관리, Qt 데이터 처리·파형 표시·decoder, 시험 자동 비교와 로그.
- **인터페이스 검토 수준:** 레지스터, FPGA 상태, 샘플 형식, DMA 완료·취소·버퍼 수명, UAPI 구조체와 오류 계약.
- **공동 검증 수준:** 실제 핀·전기 조건, 클록·리셋·IRQ 경로, DMA provider 지원, 프로토콜별 분석 가능 속도.

## 1. 전체 시스템 구조 — 신호를 검증 가능한 데이터로 바꾸는 경로

### 무엇인가

디지털 로직 분석기는 여러 입력선의 논리값을 일정한 시간 간격으로 기록하고, 그 기록을 파형과 통신 데이터로 해석하는 장치다. 전압의 연속적인 크기를 기록하는 장치와 달리 이 설계가 저장하는 값은 채널별 0과 1이다.

KR260의 **PL**은 FPGA 논리를 구현하는 영역이고, **PS**는 프로세서와 Linux가 동작하는 영역이다. **BRAM**은 PL 내부의 수집 저장소이며, **DDR**은 PS 측에서 소프트웨어가 결과를 다루는 주 메모리다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

각 단계의 역할을 구분해야 데이터가 틀렸을 때 원인을 좁힐 수 있다. v0.1의 데이터 경로는 다음과 같다. [S §1–2]

```text
STM32 외부 신호 → 입력 동기화 → 샘플링·트리거 → BRAM
                                               ↓
내부 counter8 패턴 ───────────────────────→ 수집 검증

BRAM → 32비트 AXI4-Stream → AXI DMA S2MM → PS DDR
     → logiccap 드라이버 → liblogic → 진단 CLI
                                  └→ TCP 서버 → PC Qt CaptureData
                                               ├→ 파형 표시
                                               └→ UART / I2C / SPI 해석
```

**제어 경로**는 설정·시작·상태·취소 명령이 전달되는 경로다. PC 명령은 TCP 서버와 liblogic, 드라이버를 거쳐 IP 제어로 이어진다. **데이터 경로**는 수집된 샘플이 BRAM에서 PC로 이동하는 경로다. 둘은 연결되어 있지만 동일하지 않다. 시작 명령을 수락했다고 데이터가 준비된 것은 아니다.

v0.1은 **단발 수집 후 전송**이다. N개를 BRAM에 저장한 뒤 DMA로 옮긴다. 전송 및 결과 보관 중에는 새 수집을 시작하지 않는다. 연속 스트리밍·프리트리거·압축·다중 접속은 첫 버전 범위 밖이다. 따라서 샘플링 속도와 TCP 전송 속도가 같을 필요는 없지만, 연속 수집 간 공백은 존재한다.

### 인터페이스 회의에서 확인할 것

- 각 단계에서 데이터를 소유하는 모듈과 다음 단계로 넘기는 조건은 무엇인가?
- 수집, 전송, 결과 보관을 구분하는 상태가 모든 계층에서 일관되는가?
- BRAM 원본, DDR 결과, CLI 파일, TCP 수신값을 같은 capture_id와 설정으로 추적할 수 있는가?
- 첫 버전의 단발 수집 제약과 이후 확장 기능이 요구사항에 명확히 분리되어 있는가?

### 수석연구자에게 설명할 문장

> 본 시스템은 외부 디지털 신호를 FPGA에서 일정 간격으로 수집하고, 고정된 결과를 DMA와 Linux를 통해 PC로 전달하는 단발 로직 분석기입니다. 저는 사용자 영역의 제어·전송·표시와 기준 데이터 비교를 담당하며, 단계별 동일성을 확인해 오류가 발생한 경계를 추적하도록 설계합니다.

## 2. Linux Character Device와 UAPI — 커널과 앱 사이의 계약

### 무엇인가

**Character Device**는 사용자 프로그램이 파일 디스크립터를 통해 드라이버 기능을 사용하는 장치 인터페이스다. `/dev` 경로는 일반 데이터 파일처럼 내용을 보관하는 장소가 아니라 드라이버 연산에 접근하는 진입점이다. 동작은 해당 드라이버의 계약에 따라 정해진다.

**UAPI**는 커널이 사용자 프로그램에 공개하는 API다. **ABI**는 프로그램이 실제로 주고받는 명령 번호, 구조체 크기, 필드 위치와 데이터 표현까지 포함하는 이진 호환 계약이다. 함수 이름이 같더라도 필드 크기나 정렬이 다르면 호환되지 않는다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

드라이버는 하드웨어 상태, DMA 채널과 버퍼, capture_id를 소유한다. 이양배의 프로그램은 이 자원을 직접 조작하지 않고 UAPI로 요청한다. v0.1은 단일 `/dev/logiccap0`과 통합 `logiccap.ko`를 제안한다. 두 번째 프로세스의 open은 EBUSY이며, 서버가 장치를 열고 있으면 CLI는 TCP 원격 모드를 사용한다. [S §2, §6]

`include/logiccap_uapi.h`는 커널과 앱이 함께 사용하는 계약의 기준이다. v0.1은 고정폭 정수와 reserved=0을 요구하고, raw 포인터·C enum·long을 ABI 필드로 사용하지 않도록 한다. 실제 ioctl 번호·구조체 크기·padding·32/64비트 호환 정책은 **미확정**이다.

**Padding**은 정렬을 위해 컴파일러가 필드 사이에 넣는 여백이고, **alignment**는 데이터가 배치될 주소 경계 조건이다. 구조체 메모리를 그대로 전송하면 컴파일러와 실행 환경의 배치 차이에 의존하게 된다. 커널 UAPI 구조체와 TCP wire format은 서로 별도의 계약으로 관리한다.

ioctl의 `_IOR`은 사용자 관점에서 읽는 방향, `_IOW`는 사용자에서 커널로 쓰는 방향, `_IOWR`은 양방향 전달을 나타낸다. 실제 매크로 선택은 최종 인자 구조와 함께 정한다. [Linux ioctl 문서](https://docs.kernel.org/driver-api/ioctl.html)

### 인터페이스 회의에서 확인할 것

- 공통 헤더의 작성·리뷰 책임자와 고정 시점은 언제인가?
- 각 구조체의 바이트 크기, 필드 offset, reserved 검증 방식은 무엇인가?
- ABI major 불일치와 미지원 ioctl의 반환 방식은 무엇인가?
- 단일 프로세스 소유권은 dup/fork로 공유된 파일 디스크립터에도 어떻게 적용되는가? 이 세부 동작은 보완 합의가 필요하다.
- FPGA ABI, 커널 ABI, TCP 버전의 변경을 각각 어떻게 관리하는가?

### 수석연구자에게 설명할 문장

> 커널이 하드웨어와 버퍼의 소유권을 유지하고 사용자 프로그램에는 공통 UAPI만 제공합니다. 이 경계에서 구조체 배치와 상태·오류 의미를 고정해 CLI와 서버가 동일한 동작을 사용하도록 합니다. 현재 ioctl 번호와 실제 구조체 배치는 구현 전 확정해야 합니다.

## 3. open / ioctl / read / poll / errno — 장치를 사용하는 정확한 의미

### 무엇인가

| 연산 | 일반적인 의미 | v0.1에서의 역할 |
|---|---|---|
| open | 경로에 접근하여 파일 디스크립터를 얻음 | 단일 장치 사용권 획득 |
| ioctl | 장치별 제어 요청과 메타데이터 교환 | 설정, 시작, 상태, 결과 정보, 취소, 해제 |
| read | 열린 대상에서 바이트를 읽음 | READY 결과의 원시 샘플 읽기 |
| poll | 지정 이벤트가 준비되는지 기다림 | READY 또는 ERROR/CANCELLED 감지 |
| lseek / llseek | 읽기 위치를 변경 / 드라이버 측 구현 | READY 데이터 범위의 cursor 조절 |
| close | 파일 디스크립터 참조를 해제 | 드라이버 정리 절차 후 소유권 반환 |
| errno | 실패한 시스템 호출의 오류 원인 표현 | 거절·미준비·취소·실패를 구별 |

시스템 호출이 실패했을 때 반환값과 함께 errno를 해석한다. 성공한 호출 뒤에 남아 있는 errno를 오류로 판정하지 않는다. `poll()`의 반환값은 데이터 길이가 아니라 이벤트가 있는 항목 수이며, 실제 원인은 `revents`와 상태 조회로 확인한다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

v0.1 정상 호출 흐름은 다음과 같다. [S §6–7]

```text
open → GET_CAPS → CONFIG → START → poll / GET_STATUS
     → GET_RESULT → read로 전체 결과 읽기 → RELEASE → close
```

START는 비동기 수집을 시작하고 capture_id를 반환한다. READY 전 `read`는 EAGAIN이다. READY의 `read`는 부분 읽기를 지원하므로 반환된 바이트 수를 누적하고 cursor를 따라 끝까지 읽는다. 결과 끝의 0은 해당 결과의 EOF이며 장치 고장을 뜻하지 않는다. 사용자에게 약속된 payload_bytes를 채우기 전에 끝났다면 길이 불일치로 다뤄야 한다.

| 상태·오류 | v0.1 의미 | 사용자 프로그램의 대응 |
|---|---|---|
| EBUSY | 다른 사용자가 장치 소유, 또는 현재 상태가 연산을 허용하지 않음 | 소유권·현재 상태를 확인하고 임의 강제 초기화를 하지 않음 |
| EAGAIN | 아직 READY 아님 | poll 또는 상태 확인 후 재시도 |
| EINVAL | 설정이 허용 범위·조합을 벗어남 | 입력을 수정하고 유효 설정이 유지됐는지 확인 |
| EIO | 오류 결과 | 상세 error_code와 복구 상태 확인 |
| ECANCELED | 취소된 결과 | 성공 데이터로 사용하지 않음 |
| ESTALE | 현재 작업과 capture_id 불일치 | 오래된 결과·요청을 배제하고 상태 재동기화 |

READY는 POLLIN, ERROR와 CANCELLED는 POLLERR로 알린다는 것이 제안 계약이다. POLLERR만으로 취소와 오류를 구별할 수 없으므로 GET_STATUS가 필요하다. READY 결과는 RELEASE 전까지 보관되고, 그동안 START를 거부한다. `close`는 전송·callback 정리가 끝나기 전에 버퍼를 없애는 단순 지름길이 아니다.

**추가 합의:** O_NONBLOCK 여부와 무관한 read 정책인지, 신호에 의한 EINTR 처리, poll timeout 이후 취소 여부, EOF 시 poll 준비 상태를 명시해야 한다. poll 대기시간 만료와 드라이버가 판정한 수집 timeout은 서로 다른 사건이다.

### 인터페이스 회의에서 확인할 것

- 상태별 허용 연산과 반환 오류를 표로 검증할 수 있는가?
- 부분 read, EOF, lseek 범위, START/RELEASE의 cursor 초기화를 함께 시험하는가?
- CANCEL 요청 수락과 취소 정리 완료를 어떤 상태로 구별하는가?
- ERROR/CANCELLED 뒤 RELEASE와 복구 실패 lockout은 어떻게 연결되는가?

### 수석연구자에게 설명할 문장

> 사용자 프로그램은 시작 요청과 결과 준비를 분리합니다. 준비 이벤트 뒤에도 상태와 결과 길이를 확인하며, 부분 읽기를 누적해 완전한 결과만 공개합니다. 취소·오류·오래된 작업 ID는 서로 다른 조건으로 처리합니다.

## 4. FPGA Register — 하드웨어 제어·관측 지점

### 무엇인가

**Register**는 하드웨어 설정이나 상태를 담는 작은 저장 단위다. **MMIO**는 CPU 주소 공간의 특정 범위를 장치 레지스터로 연결하는 방식이다. 주소를 읽거나 쓰는 행위가 하드웨어 동작과 연결되므로 일반 메모리 변수처럼 취급하지 않는다.

**Base address**는 장치 주소 영역의 시작점, **offset**은 그 안에서 개별 레지스터의 위치다. **RO/RW/WO**는 읽기 전용/읽고 쓰기/쓰기 전용을 뜻한다. **W1C**는 1을 쓴 비트만 지우는 규칙이다. **Write-one pulse**는 1을 쓴 명령 비트로 일회성 동작을 요청하는 방식이다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

진단 콘솔은 설정·상태·카운터를 관측하여 수집 IP가 요청대로 동작했는지 확인한다. 다만 콘솔이 MMIO에 직접 접근하지 않고 드라이버의 허용된 진단 API를 사용한다. [S §4, §6, §9]

| 분류 | v0.1 레지스터 | 의미 |
|---|---|---|
| 식별·능력 | IP_ID, ABI_VERSION, CAPABILITIES | 연결한 IP와 지원 기능 확인 |
| 실제 구성 | SAMPLE_CLK_HZ, MAX_SAMPLES | 시간축과 설정 상한의 근거 |
| 수집 설정 | SAMPLE_DIV, SAMPLE_COUNT_REQ, TRIGGER_CFG, INPUT_SOURCE | 간격·개수·시작 조건·신호원 |
| 명령·상태 | COMMAND, STATE | ARM/ABORT/SEND/CLEAR 및 진행 상태 |
| 관측 | SAMPLES_CAPTURED, STREAM_BYTES_SENT, TRIGGER_SEEN | 저장·전송·트리거 진행 근거 |
| 이벤트·오류 | IRQ_STATUS, IRQ_ENABLE, ERROR_FLAGS | 알림 원인과 오류 기록 |
| BRAM 진단 | BUF_RD_INDEX, BUF_RD_DATA | DMA 이전 저장 데이터 확인 |

상대 offset은 [S §4]에 제안되어 있지만 실제 base address는 미확정이다. 32비트·4바이트 정렬 접근이 제안되며, 설정은 IDLE에서만 바꾼다. 진단 쓰기는 수집 설정 4종만 허용하고 COMMAND·DMA 주소·IRQ 제어는 드라이버 내부 전용이다.

W1C 레지스터에 읽은 값 전체를 무심코 되쓰면 지울 의도가 없던 이벤트까지 확인 처리할 수 있다. 사건이 새로 발생하는 순간과 clear가 겹칠 때는 새 사건을 보존한다는 것이 v0.1 규칙이다.

### 인터페이스 회의에서 확인할 것

- offset·접근 권한·리셋값이 RTL, 드라이버, 문서에서 일치하는가?
- 잘못된 설정은 이전 값을 유지하는가? ERROR_FLAGS 발생과 치명적 ERROR 상태를 구별하는가?
- BRAM peek가 CAPTURED/STREAM_DONE에서만 가능하며 전송과 읽기 포트를 경쟁하지 않는가?
- 진단 설정 쓰기가 드라이버의 cached configuration에도 반영되는가?

### 수석연구자에게 설명할 문장

> 레지스터는 하드웨어를 제어하고 진행 상황을 관측하는 계약입니다. 콘솔은 허용된 설정과 진단 항목만 드라이버를 통해 접근하며, 수집 개수와 전송 바이트를 분리해 확인합니다.

## 5. FPGA State와 Trigger — 언제 무엇을 해도 되는가

### 무엇인가

**상태 머신**은 현재 단계에 따라 허용 명령과 다음 단계를 정하는 모델이다. **트리거**는 기록의 시작 조건이다. 엣지 트리거는 연속으로 관측한 두 값 사이의 상승 또는 하강을 판단한다.

입력 동기화는 비동기 신호가 FPGA 클록 도메인으로 들어올 때 메타안정성 전파 확률을 낮춘다. 2단 동기화가 짧은 펄스 검출이나 서로 다른 채널의 동시 전이를 완벽히 보장하는 것은 아니다. [S §3]

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

v0.1 FPGA 상태는 다음과 같다.

```text
IDLE → ARMED → CAPTURING → CAPTURED → STREAMING → STREAM_DONE
                 취소·오류 경로: ABORTED / ERROR
```

소프트웨어 상태는 `IDLE, ARMED, CAPTURING, TRANSFER_PENDING, TRANSFERRING, READY, CANCELLED, ERROR`다. FPGA와 소프트웨어 상태는 이름을 일대일로 치환할 수 없다. FPGA STREAM_DONE은 마지막 AXI beat가 수락되었다는 뜻이고, READY는 DMA 결과 검증과 CPU 접근 준비까지 끝났다는 뜻이다. [S §6–7]

샘플링은 기준 클록을 새로 나누어 클록선으로 쓰는 방식이 아니라 **clock enable**인 sample_ce를 D클록마다 발생시키는 제안이다. 입력 동기화는 매 기준 클록에서 동작하고, 저장·트리거 관측은 sample_ce를 따른다.

ARM 이후 첫 sample_ce는 D번째 기준 클록에 발생한다. 즉시 모드는 그 입력을 sample[0]으로 저장한다. 엣지 모드는 첫 sample_ce를 이전 값 초기화에만 사용하고 두 번째부터 비교한다. 검출된 현재 샘플이 sample[0]이다. 프리트리거가 없으므로 trigger_index=0이며 트리거 전 데이터는 기록하지 않는다.

### 인터페이스 회의에서 확인할 것

- 트리거가 외부 핀의 연속시간 엣지가 아니라 sampled edge라는 점이 합의됐는가?
- ARM 이전의 엣지와 첫 baseline 샘플을 어떻게 처리하는가?
- STREAMING 중 ABORT/CLEAR가 거절될 때 드라이버가 수행할 복구 절차는 무엇인가?
- 트리거 대기, N개 수집, DMA 전송의 timeout 시작점과 원인을 별도로 기록하는가?

### 수석연구자에게 설명할 문장

> 트리거는 샘플링 시점의 이전 값과 현재 값을 비교해 판정하며, 검출한 샘플부터 N개를 저장합니다. 하드웨어 저장·전송 상태와 소프트웨어 결과 준비 상태를 구분해 미완료 결과가 정상 데이터로 보이지 않도록 합니다.

## 6. Sample Format — 모든 계층이 보존해야 하는 데이터 의미

### 무엇인가

**Sample**은 한 샘플링 시점에서 관측한 전체 채널 값이다. v0.1은 한 시점의 8채널을 한 바이트로 표현하며 bit k가 CHk다. 따라서 한 샘플은 특정 채널의 통신 바이트가 아니라 8개 입력선의 순간 논리값이다.

**Packing**은 여러 샘플 바이트를 전송 폭에 맞춰 묶는 것이다. **Byte order**는 다중 바이트 수의 바이트 순서이고, **bit order**는 통신 비트가 시간상 전달되는 순서다. 이 둘과 채널 비트 배치는 서로 다른 규칙이다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

v0.1에서 N은 샘플 수이면서 원시 데이터 바이트 수다. 4개 샘플이 AXI4-Stream 32비트 word 하나에 들어간다. [S §1, §5, §10]

| TDATA 구간 | 들어가는 샘플 |
|---|---|
| bits 7:0 | sample[4j] |
| bits 15:8 | sample[4j+1] |
| bits 23:16 | sample[4j+2] |
| bits 31:24 | sample[4j+3] |

BRAM에서 DDR, CLI 파일, Qt까지 sample[0], sample[1], … 순서가 보존되어야 한다. AXI word의 정수 표기와 메모리 바이트 배열의 나열을 혼동하지 않는다. TCP의 다중 바이트 정수 헤더를 big endian으로 인코딩하더라도 원시 샘플 바이트를 역순으로 바꾸지 않는다.

### 인터페이스 회의에서 확인할 것

- bit k → CHk → 실제 커넥터 핀 → STM32 핀 연결표가 있는가?
- N의 단위가 sample, byte, beat 중 무엇인지 모든 필드에 표시했는가?
- DMA 후 메모리 바이트 순서를 counter8으로 확인했는가?
- 파일에 원시 데이터만 저장할 때 실제 클록·분주·채널·트리거 메타데이터는 어디에 보관하는가? 저장 컨테이너는 추가 확정이 필요하다.

### 수석연구자에게 설명할 문장

> 한 샘플은 같은 시점의 8채널 논리값을 담는 한 바이트입니다. 전송 과정에서 네 샘플씩 묶지만, 사용자에게 제공하는 순서는 원래 시간 순서와 채널 비트 배치를 그대로 유지합니다.

## 7. AXI4-Lite와 AXI4-Stream — 제어 접근과 샘플 전송

### 무엇인가

**AXI4-Lite**는 주소를 지정하여 레지스터를 읽고 쓰는 인터페이스다. **AXI4-Stream**은 주소 필드 없이 순서 있는 데이터를 보내는 인터페이스다. 이 프로젝트에서는 Lite가 수집 IP 제어, Stream이 BRAM 결과 전송에 쓰인다. 두 인터페이스를 역할로 구분한 것이며 AXI 전체를 두 종류만으로 분류한 것은 아니다.

**Handshake**는 송신과 수신이 같은 클록에서 데이터 전달을 수락하는 조건이다. **Backpressure**는 수신 측이 준비되지 않아 송신 진행을 멈추는 흐름 제어다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

AXI4-Lite의 쓰기 주소 AW와 쓰기 데이터 W는 독립적으로 도착할 수 있다. 응답 R/B도 상대측 준비 상태의 영향을 받는다. v0.1은 이런 지연과 WSTRB 부분 쓰기를 처리하도록 요구한다. 이양배는 RTL을 모두 작성하기보다 지연 조건에서도 레지스터 값이 보존되는지 진단 결과를 이해해야 한다. [S §4]

AXI4-Stream의 계약은 다음과 같다. [S §5]

- **TDATA:** 네 샘플을 담은 32비트 데이터.
- **TVALID:** 송신부가 유효 데이터를 제공한다는 표시. TREADY가 먼저 올라오기를 기다려서만 세우면 안 된다.
- **TREADY:** DMA 수신부가 이번 데이터를 받을 수 있다는 표시.
- **전송 성립:** TVALID와 TREADY가 함께 1인 클록에서만 한 beat가 전달됨.
- **TKEEP:** 유효한 바이트 lane 표시. N이 4의 배수인 v0.1은 항상 0xF.
- **TLAST:** 이번 beat가 capture packet의 마지막이라는 표시. 수락될 때까지 유지.

TVALID=1, TREADY=0이면 데이터와 TKEEP/TLAST를 고정하고 인덱스를 진행시키지 않는다. N bytes는 N/4 beats이며, 하나의 capture는 하나의 Stream packet이다. 수집 완료 후 전송하므로 전송 stall이 이미 기록한 샘플의 시간 간격을 바꾸지 않는다. 다만 결과 전달 지연은 증가한다.

### 인터페이스 회의에서 확인할 것

- 전송 카운터는 유효 표시 횟수가 아니라 handshake 횟수로 증가하는가?
- 마지막 beat에서 stall이 걸려도 TLAST와 데이터가 유지되는가?
- IF-06에서 무작위 TREADY 지연을 넣어 중복·누락과 TLAST 수락 횟수를 확인하는가?
- BRAM 읽기 지연을 흡수할 staging register와 reset 동작이 정해졌는가?

### 수석연구자에게 설명할 문장

> 레지스터 제어는 AXI4-Lite로, 수집 데이터는 AXI4-Stream으로 분리합니다. Stream은 양측이 수락한 클록에서만 진행하며, DMA가 대기시키는 동안 데이터와 마지막 표시를 유지해 샘플 누락을 방지합니다.

## 8. DMA / IRQ / DDR — 전송 완료와 결과 유효성을 구분하기

### 무엇인가

**DMA**는 CPU가 샘플마다 복사 명령을 수행하지 않아도 하드웨어가 데이터를 메모리로 옮기는 방식이다. CPU와 드라이버는 여전히 버퍼 준비, 전송 시작, 완료 판정, 오류 복구에 관여한다. “CPU 개입이 전혀 없다”는 설명은 정확하지 않다.

**S2MM**은 Stream-to-Memory-Mapped 방향이다. **DMAengine**은 Linux의 DMA 사용 API이며 **provider**는 DMA 하드웨어를 제어하는 드라이버, **client**는 전송을 요청하는 드라이버다. 이 설계의 logiccap은 client 역할을 맡고, 기존 provider가 DMA 레지스터와 채널을 관리한다.

**IRQ**는 하드웨어 사건을 CPU에 알리는 인터럽트다. **Callback**은 소프트웨어가 완료를 전달하는 함수 호출이다. 수집 IP IRQ 횟수, DMA 하드웨어 IRQ 횟수, DMA callback 횟수는 같은 측정값이 아니다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

v0.1 정상 흐름은 수집 완료 확인 → DMA N bytes 수신 준비 → submit·issue → IP SEND → DMA 및 Stream 완료 검증 → CPU 접근 준비 → READY다. DMA 준비 실패 시 SEND하지 않는다. [S §7]

| 관측 사건 | 확인된 의미 | 아직 단독으로 보장하지 않는 것 |
|---|---|---|
| CAPTURE_DONE | BRAM 수집 완료 사건 | DDR 전송 완료 |
| STREAM_DONE | 마지막 Stream beat 수락 | CPU가 읽을 수 있는 정상 DDR 결과 |
| DMA 완료 통지 | DMA 전송 완료 처리 발생 | 모든 상위 결과 조건 충족 |
| READY | 길이·상태·DMA·CPU 접근 준비를 검증한 공개 상태 | 외부 신호 해석값의 정확성은 별도 시험 필요 |

**버퍼 수명**은 DMA가 접근할 수 있는 동안 메모리가 유효하게 유지되어야 한다는 뜻이다. **Cache coherency/synchronization**은 장치가 쓴 결과를 CPU가 올바르게 관측하도록 접근 규칙을 지키는 문제다. CPU 가상주소와 DMA 주소를 동일하게 간주하지 않는다. 실제 coherent allocation 또는 mapping 방식은 구현에서 확정해야 한다.

DMAengine에서는 전송 제출과 issue를 구분하며, 종료 뒤 callback과 메모리 수명을 함께 정리해야 한다. 지원되는 동기 종료 API는 실제 provider와 커널 버전에 대조한다. [Linux DMAengine client API](https://docs.kernel.org/driver-api/dmaengine/client.html)

**Residue**는 전송 잔여량 정보다. v0.1은 provider가 유효하게 지원할 때 residue=0을 검사하며, 미지원 값을 0으로 꾸미지 않는다. 단발 애플리케이션이라는 이유로 DMA IP가 반드시 Simple 모드여야 하는 것은 아니다. Simple/SG 선택과 reset 연결은 미확정이다. [S §5, §7, §12]

### 인터페이스 회의에서 확인할 것

- 사용 커널/provider의 모드·주소 폭·길이 폭·completion/residue 지원을 확인했는가?
- READY의 모든 조건과 관측 순서는 무엇인가?
- CANCEL/timeout 때 DMA와 늦은 callback을 멈춘 뒤 버퍼를 반환하는가?
- 복구 실패 시 RECOVERY_FAILED로 START를 막고 최초 오류와 복구 실패를 별도로 보존하는가?
- IP reset과 DMA reset의 실제 연결·순서를 fault injection으로 검증했는가?

### 수석연구자에게 설명할 문장

> DMA는 샘플 복사 부담을 줄이지만 완료 판정과 메모리 소유권 관리는 드라이버 책임입니다. Stream 완료만으로 결과를 공개하지 않고 DMA·길이·하드웨어 상태·CPU 접근 조건을 확인한 뒤 READY로 전환합니다. 취소 경로도 정상 경로와 같은 수준으로 검증해야 합니다.

## 10. TCP Framing / Partial recv / Endianness — 바이트 흐름에서 메시지 복원하기

### 무엇인가

**TCP**는 연결 내에서 순서 있는 바이트 흐름을 전달한다. 애플리케이션이 한 번에 보낸 메시지의 경계를 수신 호출에 보존하지 않는다. **Framing**은 바이트 흐름에서 메시지 시작·길이·종류를 구별하는 규칙이다.

**Partial recv**는 요청한 길이보다 적은 바이트를 한 번에 받는 상황이다. 여러 메시지가 한 번에 읽힐 수도 있다. **Partial send**는 한 번의 송신 호출로 요청한 모든 바이트가 처리되지 않는 상황이다. 송신도 남은 길이와 위치를 추적해야 한다.

**Endianness**는 다중 바이트 정수의 바이트 배열 순서다. 네트워크 순서인 big endian과 원시 샘플의 시간 순서는 별도 규칙이다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

v0.1은 TCP 5000, 한 개 제어 세션, 다음 16-byte 헤더를 제안한다. [S §8]

| offset | 길이 | 필드 |
|---|---|---|
| 0 | 4 | ASCII magic LKLA |
| 4 | 2 | protocol_version |
| 6 | 2 | message_type |
| 8 | 4 | payload_length |
| 12 | 4 | request_id |

헤더 정수는 big endian, 제어 payload는 UTF-8 JSON이다. JSON 숫자는 바이너리 정수 필드가 아니라 텍스트 표현이다. 제어 payload 상한은 16 KiB, DATA payload 상한은 MAX_SAMPLES+12 bytes다. 길이·타입을 검증한 뒤 메모리를 할당한다.

수신기는 바이트를 누적하고 완전한 헤더를 기다린 뒤, 검증된 payload 길이만큼 모아 프레임을 완성한다. 처리 후 남은 바이트로 다음 프레임을 계속 파싱한다. `read_exact`는 필요한 길이를 모으는 논리이며 GUI 스레드를 반드시 blocking 방식으로 대기시키라는 뜻이 아니다.

**request_id**는 요청과 응답을 연결한다. **capture_id**는 수집 결과를 식별한다. 하나의 capture에 STATUS·FETCH 등 여러 요청이 연결될 수 있으므로 두 ID를 대체해서 사용할 수 없다.

FETCH 성공은 같은 request_id의 메타데이터 응답 뒤 DATA 한 프레임이다. 사이에 다른 응답을 끼워 넣지 않는다. DATA는 big-endian u32 세 개인 capture_id/sample_offset/sample_count의 12-byte prefix와 N개의 원시 바이트다. v0.1은 offset=0, payload_length=12+N이며 애플리케이션 차원의 DATA 분할은 없다. 그래도 TCP 수신은 임의로 분할될 수 있다.

### 인터페이스 회의에서 확인할 것

- 1바이트씩 도착하는 헤더·본문과 여러 프레임 병합을 모두 처리하는가?
- FETCH 메타데이터와 DATA의 ID·개수·길이를 대조하는가?
- 여러 worker의 응답이 섞이지 않도록 송신을 직렬화하는가?
- 단절 시 미완성 결과를 폐기하고 서버의 작업을 취소·해제하는가?
- 헤더/본문 수신 기한, request_id 재사용, 요청 동시 처리 범위, JSON 필드 누락·미지 필드 정책은 무엇인가? 원문에 없는 세부 규칙은 보완 합의가 필요하다.

### 수석연구자에게 설명할 문장

> TCP 위에 고정 헤더와 길이 기반 프레임을 정의해 메시지 경계를 복원합니다. 네트워크 도착 단위와 무관하게 데이터를 누적하고 요청 ID와 수집 ID, 메타데이터와 실제 길이를 대조하여 서로 다른 결과의 혼합을 방지합니다.

## 11. Mock Capture와 Mock Server — 보드 없이 계약을 검증하기

### 무엇인가

**Mock Capture**는 실제 하드웨어 대신 정해진 샘플·메타데이터·상태를 제공하는 시험 입력 또는 backend다. **Mock Server**는 실제 TCP 규약으로 이 데이터를 제공하는 대체 서버다. 원시 파일을 읽는 시험과 네트워크를 통과하는 시험은 검증하는 경계가 다르다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

Mock은 샘플 바이트뿐 아니라 실제 클록, 분주, trigger_index, channel_count, capture_id를 함께 제공해야 한다. 정상 데이터만 항상 즉시 반환하면 미준비 상태와 취소·단절 처리를 검증할 수 없다.

**보완 제안:** READY 지연, timeout, CANCELLED, 오래된 ID, 잘못된 길이, 헤더·본문 분할과 단절을 재현할 수 있게 한다. Mock과 실제 서버가 동일한 fixture를 사용하되, 기대값 생성과 decoder 구현을 무조건 같은 코드로 공유하지 않는다. 같은 버그로 서로 맞아 보일 수 있기 때문이다.

- Mock의 상태·오류가 실제 UAPI와 동일한 의미인가?
- Mock 합격과 실제 전기 입력·DMA 합격을 별도 항목으로 관리하는가?

### 수석연구자에게 설명할 문장

> Mock은 보드 없이 사용자 프로그램의 데이터 계약과 오류 처리를 검증하기 위한 환경입니다. 동일 fixture를 네트워크·화면·분석에 재사용하되, 실제 샘플링과 DMA의 하드웨어 검증은 별도로 수행합니다.

## 12. Qt Network / Data / View 분리 — 수신과 해석과 표시의 책임

### 무엇인가

**Network**는 연결·프레임 복원·요청 응답을 담당한다. **Data**는 검증된 메타데이터와 원시 샘플을 보관한다. **View**는 데이터를 파형·문자로 표시한다. **Decoder**는 원시 샘플을 통신 의미로 변환한다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

v0.1의 `CaptureData`는 메타데이터와 QByteArray sample bytes를 함께 보관한다. decoder는 socket이나 드라이버에 직접 접근하지 않고 CaptureData와 설정만 받는다. [S §10]

`QTcpSocket`은 TCP 연결을 다루며 `QByteArray`는 바이트 저장에 적합하다. `readyRead`는 읽을 데이터가 있다는 알림이지 완전한 프레임 도착 알림이 아니다. signal/slot은 사건과 처리 함수를 연결한다. 비동기 수신에서는 누적 버퍼와 parser 상태를 유지해야 한다. [Qt QAbstractSocket 문서](https://doc.qt.io/qt-6/qabstractsocket.html)

Network는 FETCH 전체 검증 전까지 임시 수신 상태를 유지하고, 완성된 CaptureData를 표시·분석에 전달하는 구성이 적절하다. View의 채널 숨김이나 확대·축소가 원시 데이터의 채널 번호·샘플 수를 바꾸면 안 된다.

**보완 제안:** 오래 걸리는 분석은 worker에서 수행하고 GUI 갱신은 GUI 스레드에서 처리한다. socket의 소속 스레드와 이벤트 루프를 명확히 하며, 다른 스레드에서 임의 접근하지 않는다. 네트워크 자체에 무조건 별도 스레드가 필요한 것은 아니고, GUI를 막지 않는 처리 구조가 핵심이다. 구체적인 QThread 구성은 원문에서 확정하지 않았다.

### 인터페이스 회의에서 확인할 것

- CaptureData에 실제 클록·분주·N·trigger_index·인코딩·채널 수가 함께 있는가?
- 수신 도중의 데이터와 표시 가능한 완료 데이터를 구별하는가?
- 늦게 끝난 이전 capture의 decode 결과가 새 화면을 덮어쓰지 않는가?
- 저장 파일을 직접 읽었을 때와 TCP로 받았을 때 같은 분석 결과가 나오는가?

### 수석연구자에게 설명할 문장

> 네트워크 수신, 원시 데이터 모델, 표시와 분석을 분리합니다. 파형과 decoder가 같은 CaptureData를 사용하므로 네트워크 없이도 검증할 수 있고, 표시 설정이 원본 데이터를 변경하지 않습니다.

## 13. Waveform / Time Axis / Channel Extraction — 바이트를 시간상의 논리값으로 표시하기

### 무엇인가

**Waveform**은 샘플의 논리값을 시간축에 배치한 표현이다. **Channel extraction**은 한 샘플 바이트에서 특정 채널 비트를 꺼내는 연산이다. 화면의 픽셀 위치와 원본 샘플 인덱스는 서로 다른 좌표다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

v0.1의 시간과 채널 정의는 다음과 같다. [S §1, §10]

```text
Fs = sample_clk_hz / sample_div
Ts = sample_div / sample_clk_hz
t(i) = i × Ts
t_trigger(i) = (i - trigger_index) × Ts
CHk(i) = (sample[i] >> k) & 1
```

Fs는 샘플률, Ts는 샘플 간격이다. 시간축은 목표 100 MHz를 상수로 쓰지 않고 해당 capture의 실제 기준 클록과 분주를 사용한다. 시간 계산에서 정수 나눗셈으로 소수 부분을 잃지 않도록 한다.

N개 샘플의 기록 구간 길이는 N×Ts이며, 첫 샘플과 마지막 샘플 시각 차이는 (N−1)×Ts다. 두 값은 목적이 다르다. 커서 간 시각 차이는 해당 인덱스 차이에 Ts를 곱한다. 디지털 샘플만으로 실제 전압 전이의 정확한 연속시간 위치를 알 수는 없다.

확대·축소는 표시 변환이다. 축소 시 샘플 하나만 골라 그리면 짧은 펄스가 화면에서 사라질 수 있다. **보완 제안:** 화면 픽셀 구간 내 전이 존재를 보존하는 표시 방법을 정하고, decoder는 화면용 축약 데이터가 아닌 원본으로 동작시킨다.

### 인터페이스 회의에서 확인할 것

- trigger-relative 시간 원점과 기록 길이 표기가 명확한가?
- 채널 숨김·재배열 후에도 bit k의 의미가 유지되는가?
- 최대 N에서 확대·축소·커서 응답성의 합격 기준은 무엇인가?
- decoder의 `[start_sample, end_sample_exclusive)` 구간과 화면 강조 구간이 일치하는가?

### 수석연구자에게 설명할 문장

> 파형은 실제 클록과 분주로 계산한 샘플 시간축에 채널 비트를 표시합니다. 확대·축소는 표시만 바꾸며 원본과 분석 입력은 보존합니다. 기록 길이와 첫·마지막 샘플의 시각 차이도 구분합니다.

## 14. UART Decoder — 샘플에서 비트 경계를 추정하고 프레임을 해석하기

### 무엇인가

**UART**는 별도 공유 클록선 없이 baud 설정에 따라 비트 시간을 해석하는 비동기 직렬 통신이다. start bit로 프레임 시작을 찾고, data bits·선택적 parity·stop bits를 해석한다. **8N1**은 데이터 8비트, parity 없음, stop 1비트다.

**Baud**는 심벌 속도다. 일반적인 이진 UART에서 한 심벌은 한 비트를 표현하지만, start/stop/parity 오버헤드 때문에 baud를 사용자 payload 바이트 전송률로 바로 바꿀 수는 없다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

v0.1은 UART를 첫 decoder로 두고 RX 채널, baud, data bits, parity, stop bits, idle polarity를 설정으로 정의한다. 기본 검증은 115200 baud, 8N1, idle high다. [S §10]

Decoder는 지정 채널의 idle에서 start로 향하는 전이를 찾고, 설정된 비트 주기를 기준으로 비트 중앙에 가까운 샘플을 판정한다. 일반 UART 데이터는 LSB first로 조립한다. stop과 parity 조건을 확인한 뒤 값과 오류를 기록한다. 비트당 샘플 수 `Fs/baud`가 정수가 아닐 수 있으므로 매 비트에 잘린 정수 간격만 반복 더하면 위치 오차가 누적될 수 있다.

**Framing error**는 stop 조건 불일치 등 프레임 구조가 맞지 않는 오류다. **Parity error**는 parity 규칙 불일치다. **Incomplete**는 capture 경계 등으로 판단할 샘플이 부족한 상태다. 부족한 비트를 임의로 채워 정상 바이트로 만들지 않는다.

원문은 decoder 결과에 protocol, start_sample, end_sample_exclusive, decoded value, error_code를 요구한다. 첫 하강 엣지로 trigger한 capture는 sample[0] 이전 idle을 포함하지 않을 수 있다. **보완 합의:** 경계의 첫 start를 어떤 메타데이터·조건으로 인정하는지 명시해야 한다. 이전 샘플이 없다는 이유로 모든 첫 프레임을 버리거나, 어떤 낮은 시작값도 start라고 단정하지 않는다.

### 인터페이스 회의에서 확인할 것

- 지원 baud·sampling ratio와 클록 오차 허용 범위는 어떤 시험으로 정하는가?
- 비트 중심 위치 계산과 경계 반올림 규칙은 무엇인가?
- 기본 8N1 외 설정은 구현 대상인가, 향후 기능인가?
- 첫 프레임의 시작 경계와 마지막 불완전 프레임을 어떻게 표시하는가?
- byte 일치뿐 아니라 오류 종류와 샘플 구간도 비교하는가?

### 수석연구자에게 설명할 문장

> UART 해석은 샘플의 전이에서 프레임 시작을 찾고, baud에 따른 비트 위치를 판정해 바이트를 조립하는 과정입니다. 값뿐 아니라 stop·parity 조건과 샘플 부족을 확인하며, 분석 가능한 속도는 실제 샘플링 비율 시험으로 입증합니다.

## 15. STM32 Fixture — 재현 가능한 기준 신호와 기대 결과

### 무엇인가

**Fixture**는 시험을 반복할 수 있도록 고정한 장치·배선·설정·입력·기대값의 묶음이다. STM32는 미리 정한 통신 신호를 생성하는 시험 장치다. 송신 firmware의 데이터가 기대값의 출발점이지만 실제 핀 신호까지 자동으로 정확하다고 보장하는 것은 아니다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

계획서는 STM32 NUCLEO-F411RE를 도구로 명시하고, 이양배에게 시험 신호와 해석값 비교를 배정한다. v0.1의 UART 기준 송신은 `55 AA 00 FF 31 32 33` 반복이다. I2C/SPI의 상대 장치·주소·배선은 미확정이다. [P; S §10, §12–13]

Fixture에는 firmware 버전, 실제 주변장치 설정, 채널 핀 연결표, 전기 조건, 송신 순서·반복 간격, 수집 설정, 기대 decode와 오류 조건이 필요하다. 신호 전압과 공통 GND, I2C pull-up은 배선 계약의 일부다. 커넥터 전원 규격만으로 입력 핀의 허용 전압을 추정하지 않는다.

**보완 제안:** 송신 데이터와 기대 결과 파일을 시험 버전으로 묶고, 필요 시 독립 측정으로 송신 핀의 타이밍도 확인한다. 반복 패턴 중 어디서 capture가 시작했는지 정렬하는 규칙을 고정한다. 단순히 어느 위치에서든 같은 짧은 패턴이 발견되었다는 이유로 전체 시험을 통과시키지 않는다.

### 인터페이스 회의에서 확인할 것

- 실제 핀·전압·GND·보드 설정이 확인된 배선표로 남았는가?
- STM32 설정값과 실제 baud/clock의 근거는 무엇인가?
- 예상 송신열과 capture에서 비교할 완전한 구간을 어떻게 정렬하는가?
- firmware 변경이 fixture 버전과 기대값에 함께 반영되는가?

### 수석연구자에게 설명할 문장

> STM32 시험은 송신값만 지정하는 것이 아니라 배선·타이밍·firmware·기대 결과를 함께 고정한 fixture로 수행합니다. 이를 통해 수집과 전송, decoder를 실제 신호 기준으로 반복 검증합니다.

## 16. I2C와 SPI — 서로 다른 클록·경계 규칙으로 해석하기

### 무엇인가

**I2C**는 SDA 데이터선과 SCL 클록선을 사용하는 통신이다. 일반적인 open-drain 구성에서는 pull-up이 High 레벨을 만들며, 장치는 Low로 당기는 방식으로 버스를 구동한다. 기본 해석은 START/STOP, 주소·R/W, 데이터, ACK/NACK를 구별한다.

**SPI**는 SCLK와 데이터선 MOSI/MISO, 선택선 CS를 사용하는 동기 직렬 통신이다. CPOL은 클록 유휴 레벨, CPHA는 데이터를 판정하는 엣지 관계를 정한다. mode 0~3은 두 조건의 조합이다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

v0.1의 구현 순서는 UART → I2C → SPI다. I2C 초기 검증은 7-bit 주소, START/STOP, ACK/NACK, read/write 순서다. SPI 초기 검증은 mode 0, 8-bit, MSB first이며 설정 항목에는 mode 0~3, bits/word, bit order, CS polarity가 있다. 설정 목록의 존재를 모든 조합 구현 완료로 해석하지 않는다. [S §10]

| 항목 | I2C | SPI |
|---|---|---|
| 시작·종료 경계 | SCL High에서 SDA 전이로 START/STOP 판정 | CS 활성 구간과 clock edge로 판정 |
| 비트 해석 | SCL의 데이터 판정 시점에서 SDA를 읽음 | mode에 맞는 SCLK 엣지에서 MOSI/MISO를 읽음 |
| 추가 의미 | 주소와 R/W, 바이트 뒤 ACK/NACK | word 길이, bit order, 송수신 양방향 |
| 주의점 | repeated START, clock stretching, 경계 오검출 | CPOL/CPHA 불일치, CS 경계, 불완전 word |

I2C NACK는 항상 시험 실패를 뜻하지 않는다. read의 마지막 바이트를 끝내는 정상 절차일 수 있으므로 transaction 문맥과 기대값으로 판정한다. SPI mode 0은 CPOL=0, CPHA=0이며 첫 상승 엣지에서 샘플링한다. 다른 mode는 CPOL/CPHA 규칙에 따라 판정 엣지를 바꾼다.

### 인터페이스 회의에서 확인할 것

- I2C 주소 표기는 7-bit 주소인가, R/W를 포함한 첫 전송 바이트인가?
- repeated START와 clock stretching을 첫 버전에서 지원·시험하는가?
- SPI 상대 장치, CS polarity, mode, word 길이, bit order를 fixture별로 고정했는가?
- 누락된 clock edge와 capture 끝의 불완전 transaction을 정상값과 구별하는가?

### 수석연구자에게 설명할 문장

> I2C는 버스 시작·종료와 주소·응답을, SPI는 선택선과 클록 위상에 따른 비트 판정을 해석합니다. 동일한 원시 샘플 모델 위에 각각의 경계 규칙을 적용하며, 상대 장치와 배선이 정해진 fixture로 지원 범위를 검증합니다.

## 17. Expected-vs-Actual 테스트 — 일치와 실패를 재현 가능한 기준으로 판정하기

### 무엇인가

**Expected**는 명세 또는 독립된 입력 근거에서 얻은 기대 결과이며, **Actual**은 구현에서 관측한 결과다. 테스트는 두 결과를 정해진 비교 규칙으로 대조하는 과정이다. “파형이 그럴듯하다”는 인상은 합격 기준이 아니다.

### 왜 필요한가 / 프로젝트에서 어디에 쓰이는가

v0.1은 RTL → MMIO → BRAM peek → DMA → CLI 반복 → TCP → Qt → 실제 통신 순서로 검증한다. 같은 기대값을 경계마다 재사용해 최초 불일치 지점을 좁힌다. [S §9, §11]

| 시험 층 | 기대값 | 실제값 | 판단할 내용 |
|---|---|---|---|
| 내부 counter8 | sample[i]=i mod 256 | BRAM/DDR/파일의 바이트 | 길이·순서·모든 바이트 |
| 상태·오류 | 연산별 허용 상태·오류 | UAPI와 상태 로그 | 잘못된 요청 거부, 정상 결과 오공개 방지 |
| TCP | 동일 논리 프레임 | 임의 분할·병합 후 파싱 결과 | 경계·길이·ID 일치 |
| Qt | 동일 CaptureData | 표시 시간·채널·decode | 입력 경로와 무관한 결과 일치 |
| STM32 | fixture의 송신·transaction | decoder 출력 | 값·순서·오류·구간 일치 |
| 취소·복구 | 정리 후 정상 재시작 또는 명시적 lockout | 다음 수집과 메모리 상태 | 조기 해제·늦은 완료 혼입 방지 |

counter8은 결정적 바이트 비교에 적합하지만 256샘플 주기다. **보완 제안:** 길이를 유지한 채 256샘플 블록이 잘못 대체되는 일부 오류는 이 패턴만으로 식별하기 어렵다. 더 긴 주기의 알려진 패턴이나 위치 식별이 가능한 별도 fixture로 보완할 수 있다. 이것은 v0.1의 새로운 필수 기능으로 확정된 내용은 아니다.

원문은 100회 반복의 각 capture에서 N개 길이, 모든 바이트, trigger_index, 전송 카운터를 검사하도록 한다. 합격한 시행만 세거나 timeout 뒤 자동 재시도 성공으로 덮어쓰지 않는다. IF-11은 IF-05의 데이터 일치와 capture_id·로그 추적 가능성을 요구한다.

로그는 timestamp_utc, run_id, capture_id, ABI, 실제 클록, 전체 설정, 기대·실제 샘플 수, stream_bytes_sent, result, 최초 불일치 index/expected/actual, error_code, recovery_result, elapsed_ms를 포함한다. 측정하지 않은 값은 null이다.

### 성능과 정확성의 구분

정확성 합격은 데이터·상태 계약 준수이며, 성능 합격은 측정 구간과 목표 수치가 별도로 있어야 한다. 샘플링 속도는 신호 기록 간격, DMA 전송률은 메모리 이동 속도, TCP 시간은 네트워크 전달 지연, Qt 렌더링 시간은 표시 지연이다. 하나를 다른 것의 실측 근거로 대체할 수 없다.

DMA 전송률은 payload bytes를 **정의된 DMA 측정 구간**으로 나눈 값이다. trigger 대기나 전체 UI 시간을 같은 분모에 섞으면 다른 지표가 된다. [P]는 기록 시간·DMA 전송률·FPGA 자원 측정을 요구하지만 처리량 하한, UI 지연 상한, 프로토콜별 최대 검증 속도는 아직 구체적으로 확정되지 않았다.

### 인터페이스 회의에서 확인할 것

- 각 IF 시험에 입력·기대값·담당·실측 증빙 경로가 연결되어 있는가?
- 불일치 최초 위치를 BRAM·DDR·PC 중 어느 경계까지 추적할 수 있는가?
- 오류·취소·단절 시험에서도 메모리 수명과 다음 작업 성공을 확인하는가?
- 정확한 바이트 비교와 타이밍 허용 오차 비교의 판정 규칙이 분리되어 있는가?

### 수석연구자에게 설명할 문장

> 검증은 알려진 기대값을 각 계층의 실제값과 비교하는 방식으로 수행합니다. 성공 횟수뿐 아니라 최초 불일치 위치와 오류·복구 결과를 기록하고, 정확성 시험과 성능 측정을 구분하여 결과의 근거를 제시합니다.

- **석민정에게:** “trigger sample이 index 0이라는 규칙을 immediate와 edge 각각 어떤 파형으로 확인합니까? baseline 처리와 BRAM 결과를 같은 fixture로 받을 수 있습니까?”
- **신유지에게:** “READY 전에 확인하는 DMA·Stream·길이 조건은 각각 무엇이며, residue 미지원 환경에서는 어떤 관측값으로 검증합니까?”
- **드라이버 공동 담당에게:** “ERROR/CANCELLED 이후 RELEASE와 RECOVERY_FAILED lockout의 허용 관계를 상태별 표와 UAPI 시험으로 확정할 수 있습니까?”
- **팀 전체에게:** “실제 핀·클록·커널 버전이 고정된 뒤 어떤 IF 시험 증빙이 있어야 인터페이스 v1을 승인합니까?”

이는 질문 문장을 외우기 위한 목록이 아니라 **계약 → 구현 → 시험 → 증빙**의 연결을 확인하는 방식이다.

## 19. 학습 순서와 이해 완료 기준

| 순서 | 학습 범위 | 이해 완료 기준 | 남길 산출물 |
|---|---|---|---|
| 1 | 전체 구조·상태·샘플 의미 | 제어와 데이터 경로, 세 종류의 완료를 구별 | 흐름도·상태 대응표 |
| 2 | Character Device·UAPI·오류 | 상태별 호출과 실패 후 동작을 설명 | 공통 헤더 리뷰·호출/오류 표 |
| 3 | AXI·DMA·IRQ·버퍼 수명 | handshake·READY·취소 복구를 설명 | DMA 완료 조건·경계 시험표 |
| 4 | TCP·바이너리 표현 | 임의 분할·병합에도 같은 프레임 복원 | parser 시험과 wire fixture |
| 5 | Mock·CaptureData | 보드 없이 정상·오류·취소 재현 | mock backend·샘플/메타데이터 |
| 6 | Qt·파형·시간축 | 동일 파일의 채널·시간을 정확히 표시 | 파형·커서 검증 결과 |
| 7 | UART·STM32 fixture | 송신값·오류·불완전 경계를 판정 | firmware·배선·기대 decode |
| 8 | I2C·SPI | transaction 경계와 설정 영향을 설명 | 프로토콜별 fixture·지원 표 |

Qt 화면만 완성하거나 정상 데이터 한 번을 수신했다고 통합 검증을 완료한 것은 아니다. 각 단계의 완료 기준은 다음 단계가 신뢰할 수 있는 계약과 증빙을 남기는 것이다.

## 20. 수석연구자 발표용 설명문

다음은 **설계 단계에서 사용할 설명문**이다. 실제 구현 완료 후에는 확인된 시험 ID와 측정값을 덧붙이고, 수행하지 않은 작업을 완료형으로 바꾸지 않는다.

> Lucky Kernel은 KR260 기반의 8채널 디지털 로직 분석기를 목표로 합니다. v0.1은 외부 입력을 일정 간격으로 N개 수집해 BRAM에 보관한 뒤 AXI4-Stream과 DMA를 통해 PS DDR로 전달하는 단발 구조입니다. 최대 100 MHz는 현재 목표이며, 실제 타이밍 통과와 외부 통신 분석 가능 속도는 별도로 검증해야 합니다.
>
> 커널 드라이버는 수집 IP와 DMA 버퍼의 소유권을 관리하고 공통 UAPI를 제공합니다. FPGA의 Stream 완료만으로 데이터를 공개하지 않고 DMA 완료, 길이와 하드웨어 상태, CPU 접근 조건을 확인한 뒤 READY로 전환하도록 설계했습니다.
>
> 제 담당은 이 UAPI를 사용하는 공통 라이브러리와 진단 콘솔, TCP 서버, Qt 파형·분석 프로그램입니다. TCP는 길이 기반 framing으로 분할·병합 수신을 처리하고, Qt는 네트워크와 CaptureData, 표시·decoder를 분리해 같은 원시 데이터를 독립적으로 검증합니다.
>
> 검증은 내부 기준 패턴으로 BRAM·DMA·CLI·TCP 경로의 데이터 일치를 확인한 뒤, STM32 fixture의 송신값과 decoder 결과를 비교하는 순서로 진행합니다. 반복 시험에서는 모든 바이트와 작업 ID를 추적하고, 오류와 복구 결과를 별도 기록합니다.
>
> 현재 우선 확정할 항목은 실제 핀과 전기 조건, DMA provider 및 reset 구성, 공통 UAPI의 이진 배치, fixture와 성능 합격 기준입니다. 인터페이스 승인 여부는 회의 개최가 아니라 공통 산출물과 시험 증빙으로 판단하겠습니다.

## 21. 원문·보조 근거 안내

프로젝트 수치·상태·프레임·역할의 근거는 [P]와 [S]다. 외부 문서는 일반 기술 의미를 확인하는 보조 근거이며, 프로젝트 구현 또는 채택 버전을 증명하지 않는다.

- [P] 계획서: 「배경 및 목적」「목표 및 범위」「주요 기능 및 예상 결과물」「팀 구성 및 역할」 및 마지막 담당자별 상세 역할 표.
- [S §1–3] 범위·전체 구조·입력 동기화·샘플링·트리거·FPGA 상태.
- [S §4–5] 레지스터·AXI-Lite·Stream packing·DMA 데이터 계약.
- [S §6–7] UAPI·소유권·정상 실행·취소·오류 복구.
- [S §8–10] TCP·CLI/로그·Qt·decoder·STM32 기준 신호.
- [S §11–14] IF 시험·미확정 항목·담당별 산출물·저장 구조.
- [Linux ioctl 기반 인터페이스](https://docs.kernel.org/driver-api/ioctl.html): ioctl 방향과 이진 인터페이스 검토.
- [Linux DMAengine client API](https://docs.kernel.org/driver-api/dmaengine/client.html): 전송 제출·issue·완료 및 종료 절차.
- [Qt QAbstractSocket](https://doc.qt.io/qt-6/qabstractsocket.html): 비동기 수신 알림과 socket 동작. 실제 프로젝트 Qt 버전은 미확정.

**최종 학습 판단 기준:** “무슨 기술을 썼는가”에 더해, “어떤 데이터를 누가 소유하고, 언제 유효해지며, 무엇을 비교해 정상임을 입증하는가”를 각 경계마다 설명할 수 있어야 한다.
